# C언어 기반 콘솔 요트다이스 게임 (Yacht Dice)
> 2학년 1학기 '프로그래밍 설계' 강의에서 배운 것을 활용하여 C언어로 구현한 텍스트 기반 요트다이스 게임 프로젝트 입니다.

**안내 사항: ** 본 프로젝트는 2024년도 2학년 1학기 과제물로, 취업 포트폴리오 관리를 위해 로컬 컴퓨터에 보관 중이던 소스코드를 깃허브 레포지토리로 이관한 프로젝트입니다.
---

## 1. 프로젝트 소개
* **진행 기간:** 2024.04 ~ 2024.06 (2학년 1학기, 약 2개월)
* **개발 배경 및 목적:** 강의 시간에 배운 C언어의 배열, 반복문, 조건문 등 기초 프로그래밍 기법을 고도화하고, 선택 정렬 및 탐색 알고리즘을 콘솔 환경에 적용하여 다중 플레이어가 즐길 수 있는 턴제 보드게임을 구현하고자 시작되었습니다.

## 2. 기술 스택
* **개발 언어:** C
* **운영체제 환경:** Windows 10 / 11
* **개발 도구(IDE):** Visual Studio 2022
* **사용한 라이브러리:** windows.h

---

## 3. 시작 가이드 및 실행 방법

### 빌드 및 구동 환경
* 본 프로그램은 Windows 운영체제 환경이 필요합니다. (windows.h 라이브러리 의존)
* 프로젝트 컴파일 및 빌드를 위해 Visual Studio 2022 이상 설치를 권장합니다.

### 실행 방법 
1. 본 레포지토리의 소스코드를 다운로드하거나 Clone 합니다.
2. 폴더 내의 yacht.sln 파일을 더블클릭하여 Visual Studio로 프로젝트를 엽니다.
3. Visual Studio 상단 메뉴에서 빌드 구동을 확인하거나, 단축키 Ctrl + F5를 눌러 프로그램을 컴파일 및 실행합니다.
4. 콘솔 창이 활성화되면 안내에 따라 게임을 진행합니다.

본 프로젝트는 시스템 요구사항에 맞춰 기능별로 역할을 철저히 분리하는 모듈화 아키텍처를 채택하였습니다.

## 7. 트러블 슈팅 및 문제 해결 과정

### 1) 입력 버퍼로 인한 무분별한 무한 루프 에러
* **문제점:** 주사위 굴리기 및 입력 모듈에서 사용자가 잘못된 문자나 숫자를 입력했을 때, 입력 버퍼가 비워지지 않아 프로그램이 무한 루프에 빠지거나 오작동하는 현상이 발생했습니다.
* **해결방안:** 에러 발생 직후 `while(getchar() != '\n');` 구문을 추가하여 입력 버퍼를 강제로 비워주는 예외 처리 로직을 적용해 시스템 안정성을 확보했습니다.

### 2) 통합 과정에서의 변수 다중 정의(다중 선언) 충돌
* **문제점:** 각 팀원이 독립적으로 개발한 소스 코드를 하나로 합치는 과정에서 동일한 변수명이 여러 함수에서 중복 정의되어 컴파일 에러가 발생했습니다.
* **해결방안:** 공통 변수는 main.c에서만 단일 정의하고, 서브 모듈 함수들에서는 extern 키워드를 사용해 참조하도록 설계를 전면 수정하여 변수 충돌 문제를 해결했습니다.

### 3) 한글/영어 혼합 입력 시 문자열 버퍼 오버플로우 및 레이아웃 붕괴
* **문제점:** 플레이어 이름 입력 시 2차원 배열 크기 제한을 초과하면 에러 메시지 없이 점수판 레이아웃이 완전히 깨지는 현상이 있었습니다. 아스키코드로 한글(2바이트)과 영어(1바이트)를 분리해 글자 수를 제안하려 했으나 혼합 사용 시 예외 처리가 작동하지 않았습니다.
* **당시의 해결방안:** 프로젝트 진행 당시에는 완벽한 예외 처리 해결 방안을 찾지 못하여, 게임 플레이 시 한글과 영어를 혼합해서 사용하지 않는 것으로 팀 내에서 암묵적으로 제한하고 마무리지었습니다.
* **현재 시점의 분석:** 지금 되돌아보면, 이는 멀티바이트 환경(EUC-KR/CP949)에서 한글(2바이트)과 영어(1바이트)가 섞일 때 문자열의 끝을 나타내는 널 문자(\n 또는 \0) 처리와 버퍼 메모리 크기 계산이 정밀하지 못해 발생한 문제였던 것 같습니다.

### 4) 비정상적인 거대 숫자 입력 시 프로세스 크래시 (오류 코드: -1073741819)
* **문제점:** 점수 카테고리 선택 시 1~12를 벗어나 십만, 백만 단위 이상의 비정상적으로 큰 값을 고의로 입력하면 상용 프로세스가 강제 종료되는 심각한 메모리 에러가 발생했습니다.
* **당시의 해결방안:** 입력 조건문 자체에는 논리적 오류가 없어 프로젝트 당시에는 정확한 원인을 규명하지 못했습니다. 다만 일반적인 게임 환경에서 만 이상의 거대 숫자를 입력할 일이 없을 것이라 가정하고 통과시켰습니다
*  **현재 시점의 분석:** 4학년인 지금 다시 코드를 분석해 보면, 사용자가 정수형(int) 범위를 초과하는 거대 숫자를 입력했을 때 오버플로우가 발생했거나, 잘못된 입력값이 예외 필터를 우회하여 점수판 배열의 인덱스로 그대로 참조되면서 메모리 무단 접근(Out of Bounds) 크래시가 일어난 것으로 판단됩니다.

## 8. 프로젝트를 통해 배운 점 및 개선점
* **이론과 실무의 차이:** 단순 서적을 통해 함수를 개별적으로 배우는 것과, 자원의 효율성 및 구조적 모듈화를 종합적으로 고려하여 하나의 온전한 프로그램을 완성해 나가는 실습은 천지차이라는 것을 느꼈습니다.
* **협업 및 소통 역량:** 4인 팀 프로젝트를 통해 두 달간 서로의 역할을 조율하고, 코드 충돌을 해결하며 새로운 기술적 관점을 수용하는 엔지니어링 협업 능력을 체득했습니다.
* **개선점 (Improvements):**
  * 임시 변수 남발로 인한 경제성 고려 부족: 각 모듈을 하나로 합쳤을 때 이미 채워진 칸에 점수가 중복 입력되거나, 이전 턴의 주사위 결과값이 다음 계산에 누적 합산되는 복합적인 버그들이 터져 나왔습니다. 당시에는 '프로그램의 정상 실행'이 최우선 과제였기에 원천적인 구조 개혁을 하지 못하고, 버그를 임시로 막기 위해 새로운 변수를 계속 선언하고 함수를 덧붙이는 하드코딩식 처리를 반복했습니다. 이로 인해 자원의 낭비가 심해져 소프트웨어의 경제성과 복잡도를 정밀하게 관리하지 못한 아쉬움이 남았으며, 설계 단계에서 데이터 초기화와 흐름을 꼼꼼히 정의하는 것이 얼마나 중요한지 깨달았습니다.
  * 구조체 배열 도입을 통한 중복 코드 최적화: 플레이어별 점수판을 p1score, p2score 등 개별 전역 변수 배열로 관리하면서 점수 선택 함수 내부에 대량의 switch-case 중복 코드가 발생했습니다. 플레이어의 데이터 모델(닉네임, 점수 배열, 총점)을 하나의 구조체로 정의하고 이를 배열로 관리했다면, 플레이어 번호를 배열 인덱스로 활용해 중복 로직을 획기적으로 줄이고 코드 유지보수성을 높일 수 있었을 것입니다.
  * 방어적 프로그래밍을 통한 예외 처리 고도화: 점수 선택 메뉴에서 범위를 완전히 초과하는 거대한 숫자를 고의로 입력했을 때, 인덱스 참조 범위를 벗어나 프로세스가 강제 종료되는 메모리 접근 결함(Out of Bounds)이 존재했습니다. 입력 데이터의 범위와 타입을 실행 직전에 엄격하게 제한하는 유효성 검증 로직이 선행되어야 프로그램의 신뢰성을 확보할 수 있음을 배웠습니다.
